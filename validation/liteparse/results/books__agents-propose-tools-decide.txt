Why verification matters
A coding agent can write a refund method in seconds. It compiles, and the example tests pass. Then it
ships, and it refunds money on a payment that was never captured.
Nothing about that code looked wrong. The tests only checked the inputs someone thought of, and the
review only caught what a tired reader happened to notice.
You can 't fix this by asking the agent to be more careful. Asking a second agent to review the first one doesn 't help much either. An agent can sound confident and still be wrong, so it makes a poor judge of its own work.
The core idea
Split the work three ways:
The agent proposes. It writes the change, picks what to test, runs the tools, and reads their output. The tools decide. A deterministic tool gives the same yes or no answer every time. Only tool output can block a merge.
You own the rules. You decide what " correct" means, set the thresholds, and press the merge button.
The trick is that .NET already has a deterministic tool for most questions you care about. The compiler, analyzers, unit tests, property tests, and BenchmarkDotNet each answer one question, and each answer is something an agent can read and act on.
The verification ladder
Think of these checks as a ladder. Each rung is cheaper than the one above it and catches a different kind of bug. A change climbs one rung at a time, and it only reaches a person once every tool below has said yes.

Tip. Not all output deserves the same trust. Compiler errors and seeded tests are deterministic, so they can gate a merge. Timings are statistical and need a stated tolerance. An agent' s explanation is judgment, so it informs you but never gates.
Make the compiler do the work
The cheapest check is the one you already run on every build. If you model your domain so that an illegal state can 't be written down, the compiler rejects the bug before a single test runs. People call this " make illegal states unrepresentable. "
Put each operation on its legal state
Suppose a payment' s status lives in a string, and a switch with a catch-all decides whether a refund is allowed. A new status falls into the catch-all and quietly becomes refundable. Instead, give each state its own type and put each method only where it' s legal:
public abstract record Payment(Guid Id, long Cents);
public sealed record Authorized(Guid Id, long Cents) : Payment(Id, Cents) {
public Captured Capture() => new(Id, Cents, 0);
}
public sealed record Captured(Guid Id, long Cents, long Refunded) : Payment(Id, Cents)
{
public Captured Refund(long cents) => this with { Refunded = Refunded + cents };
}
Authorized has no Refund method. If an agent tries to refund an uncaptured payment, the build fails with CS1061, which means the type has no such member:
error CS1061:
'Authorized' does not contain a definition for
'Refund'
The error names the type and the missing member. An agent can read that line and fix the code without guessing.
Let nullable analysis find missing values
Turn on nullable reference types with <Nullable>enable</Nullable> in your project file. Now string means " never null" and string? means " might be null. " The compiler warns when you dereference something that might be null (CS8602) or leave a non-nullable property unset (CS8618).
Warnings are easy to ignore, so make them count. Set TreatWarningsAsErrors to true in the project, or build with dotnet build -warnaserror. A warning is now a red build.

Gates and evidence
Each rung on the ladder becomes a gate: a check that passes or fails a change. When every gate runs from one command, the agent, you, and CI all see the same result. A green local run predicts a green pull request.

State the rule, not the example
An example test says "this input gives that output. " A property says "for every input, this rule holds. " A library such as CsCheck generates thousands of inputs, shrinks any failure to a small case, and prints a seed so you can replay it exactly.
Say you split a refund across order lines. The rule is simple: the lines add up to the refund.

using CsCheck; using Xunit;
public class SplitProperties { static readonly Gen<(long total, long[] weights)> Cases = from total in Gen.Long[1, 10 _ 000] from weights in Gen.Long[1, 10].Array[1, 6] select (total, weights);
[Fact] public void Lines _ add _ up_to _ the _ refund() => Cases.Sample(c =>
Allocator.Split(c.total, c.weights).Sum() == c.total);
}
If each line is rounded on its own, this property finds an uneven split where a cent goes missing. Example tests that only use even splits never would.
Tip. Properties are part of your spec. If an agent "fixes " a failing property by weakening it, that is a
change to the rules, and a person should decide.
The agent loop
Put the gates together and you get a loop. The agent proposes a diff. The build and analyzers run, then the tests and properties. If any gate fails, its output goes straight back to the agent as feedback. Only a change that passes every gate reaches you, along with the evidence.
Figure 2. The agent loop. Failing output becomes the agent's next prompt. This loop works because every message in it is precise. CS1061 names the type. A failed property prints the seed and the smallest failing input. The agent doesn 't need to guess what went wrong, and you don 't need to read every line to trust what passed.

Where to go next
Start small. Pick one rung you don 't use yet and add it to a single project.
Turn on nullable reference types and TreatWarningsAsErrors in one project file. Read Overview of .NET source code analysis to enable and tune the built-in analyzers. Read Testing in .NET for unit testing with xUnit, NUnit, or MSTest, and for collecting code coverage. Write one property for a method that does arithmetic, and keep the seed when it fails. For the full walkthrough, with a bug for every rung, see the Verifiable .NET guide.
Remember. Agents propose. Tools decide. You own the rules and the merge button.
