# C# port vs LiteParse

How close is `OcriaNanoDocumentExtractionClient` to LiteParse, the Rust parser it ports, running the same OCRia-nano-1 models?

- [`reference/`](reference) holds LiteParse's Markdown, generated by [`.github/workflows/liteparse-reference.yml`](../../.github/workflows/liteparse-reference.yml). It runs on a GitHub-hosted Ubuntu runner: `pip install liteparse`, `lit models pull ocria-nano`, then `lit parse --ocr-backend ocria-nano --format markdown` on:
  - every PDF and PNG under `books/`;
  - the 20 ParseBench pages in [`../parsebench/corpus.json`](../parsebench/corpus.json).
  
  The run's artifact also has LiteParse's JSON output.
- [`compare.cs`](compare.cs) runs the C# client on the same inputs and writes [`results/summary.md`](results/summary.md) plus each output as `results/<input>.txt`.

```pwsh
pwsh tools/ocria/Get-OcriaModels.ps1 -AcceptLicense
dotnet run validation/parsebench/probe.cs -- ocria   # downloads the ParseBench pages once
dotnet run validation/liteparse/compare.cs
```

To refresh the references, run the workflow (`gh workflow run liteparse-reference.yml`). Then:

```pwsh
gh run download <run-id> -n liteparse-reference -D $env:TEMP\lp
Copy-Item $env:TEMP\lp\*.md, $env:TEMP\lp\lit-version.txt validation/liteparse/reference/
```

## Results (lit 2.21.1)

Each metric runs from 0 to 1.

| Metric | What it measures | Mean |
|---|---|---|
| Recall | Share of LiteParse's distinct words that the port also produced | **0.946** |
| Precision | Share of the port's distinct words that LiteParse also produced | **0.917** |
| Order | Word-sequence LCS agreement | **0.858** |

Per input: [results/summary.md](results/summary.md).

- **Text matches on scans and images.** The six `*-scanned.pdf` books and three hero PNGs go through OCR on both sides. On these:
  - recall is 0.99–1.0 and precision 0.92–0.99;
  - order is 0.93–0.98.
  
  Line detection, recognition and line merging agree.
- **The port is ahead of LiteParse on three ParseBench pages** (ground-truth recall):

  | Page | LiteParse | Port |
  |---|---|---|
  | `dense_table_002` | 0.228 | 0.986 |
  | `timetable_page2` | 0.710 | 0.900 |
  | `complex_header_006` | 0.897 | 0.979 |

  LiteParse sends `dense_table_002` to OCR and emits the same garbage the port did before its garble fix.
- **Native pages with vector figures: LiteParse finds more.** On `tokens-explained.pdf` and its hero page, recall is 0.83–0.89. The missing words fall into two groups:
  - labels inside vector-drawn diagrams ("Normalizer", "Engine", "Decode"), which LiteParse OCRs and the port's gate skips (the OCR gate deviation);
  - link URLs, which LiteParse writes into its Markdown.
- **Reading order on complex layouts is the largest gap.** LiteParse's projection stage orders columns, sidebars and table cells. The port doesn't implement it, so:
  - order drops to 0.47 on the multi-column `baoutou` page;
  - it is 0.69–0.82 on forms, tables and annotated layouts.
  
  Every word is still there; it is the sequence that differs.

Ground-truth recall is otherwise equal or within 0.01 on the remaining ParseBench pages.
